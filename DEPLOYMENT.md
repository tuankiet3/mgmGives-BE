# Deploy backend on Render

The repository contains a Render Blueprint in `render.yaml`. The main CI/CD path builds release images with Paketo through Gradle's `bootBuildImage` task. Render temporarily uses the version-controlled Gradle multi-stage Dockerfile as a compatibility fallback, runs the service on Render's `PORT`, and checks the public database-backed `/api/categories` endpoint.

## Prerequisites

- A PostgreSQL database. Neon works well for a free demo database.
- A Vercel frontend URL.
- Credentials for Google OAuth, Webex, PayOS, and email if those integrations are part of the demo.

## Environment values

When Render creates the Blueprint, it prompts for every value marked `sync: false`.

| Variable | Value |
| --- | --- |
| `SPRING_DATASOURCE_URL` | Neon JDBC URL, for example `jdbc:postgresql://HOST/DB?sslmode=require` |
| `SPRING_DATASOURCE_USERNAME` | Database user |
| `SPRING_DATASOURCE_PASSWORD` | Database password |
| `APP_ALLOWED_ORIGINS` | Exact Vercel origin, for example `https://mgm-gives.vercel.app` |
| `FRONTEND_URL` | The same Vercel origin, without a trailing slash |
| `SEED_ADMIN_EMAIL` | Demo administrator email |
| `SEED_ADMIN_PASSWORD` | A new, strong password used only for this deployment |
| `FROM_MAIL`, `MAIL_USERNAME`, `MAIL_PASSWORD` | Verified Brevo sender, SMTP login, and SMTP key (not the Brevo account password) |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Google OAuth web client |
| `GEMINI_API_KEY` | Google AI Studio API key |
| `WEBEX_CLIENT_ID`, `WEBEX_CLIENT_SECRET` | Webex integration credentials |
| `WEBEX_REDIRECT_URI` | `https://YOUR-RENDER-SERVICE.onrender.com/api/integrations/webex/oauth/callback` |
| `PAYOS_CLIENT_ID`, `PAYOS_API_KEY`, `PAYOS_CHECKSUM_KEY` | PayOS credentials |
| `PAYOS_CANCEL_URL` | `https://YOUR-VERCEL-SITE.vercel.app/donation/cancel` |
| `PAYOS_RETURN_URL` | `https://YOUR-VERCEL-SITE.vercel.app/donation/success` |
| `PAYOS_WEBHOOK_URL` | `https://YOUR-RENDER-SERVICE.onrender.com/api/donations/payos/webhook` |

`JWT_SECRET` is generated by Render and must not be copied into the repository.

The Blueprint uses Brevo SMTP on port `2525`, sets the Google callback to
`https://mgm-gives-api.onrender.com/login/oauth2/code/google`, and tries
`gemini-flash-latest` before the stable `gemini-3.6-flash` fallback.

## Recommended deployment order

1. Create the PostgreSQL database and copy its connection values.
2. For a database previously managed by Flyway, complete the backup and V44 checks in [DATABASE_MIGRATION.md](DATABASE_MIGRATION.md).
3. Deploy this repository from the `develop` branch as a Render Blueprint.
4. Deploy the frontend and set `VITE_API_URL` and `VITE_WS_URL` there.
5. Update `APP_ALLOWED_ORIGINS`, `FRONTEND_URL`, and provider callback URLs with the final public domains, then redeploy the backend.
6. Verify `GET /actuator/health`, Liquibase's `DATABASECHANGELOG`, login, refresh-token flow, WebSocket notifications, OAuth callbacks, and payment webhooks.

## Free-tier limitation

Render's free filesystem is ephemeral. Files written to `/tmp/mgm-gives-media` disappear after a restart or redeploy. The current setup is suitable for a recruiter demo, but durable media requires moving uploads to object storage such as Cloudinary or Supabase Storage. A Render persistent disk is not available on the free service.

The frontend and backend are hosted on different origins and authentication uses credentials, so `APP_ALLOWED_ORIGINS` must contain explicit trusted origins. Do not use `*`.
